# V8.8.1 implementation notes — inspection workflow

## Inspection form expectations

1. Select a real inspection outcome; the default placeholder cannot be saved.
2. Enter a whole-number finding count of zero or more.
3. A clean Pass must use zero findings and Follow-up = No.
4. Fail / Pass with findings needs at least one finding, Follow-up = Yes, failed-item details and immediate-control notes.
5. Not completed requires a reason in Inspection notes.
6. A selected photo or document may be attached through the existing private attachment workflow. Evidence reference remains an optional field.

“Immediate controls taken” records what was done immediately; it does not replace a permanent corrective measure. Linked action draft prompts the owner to make the permanent correction, attach objective evidence, and verify effectiveness before closure.

## Duplicate guard migration

`supabase/v8.8.1-linked-action-deduplication.sql` is a candidate migration for review only. It uses a security-definer trigger with a fixed search path and tenant-scoped advisory transaction locks. It normalizes description punctuation/case, excludes terminal actions, skips unlinked standalone actions and avoids rechecking an unchanged duplicate signature on ordinary edits to an active record.

Apply only in staging after confirming the target schema and role permissions, then test concurrent duplicate submissions and edits to legacy records. Back up before any production migration. The UI duplicate check alone is bypassable via direct API/RPC, so do not count it as server-side protection.


## Corrective-action work queue

The actions register adds owner, priority and deadline filters. Deadline buckets are: overdue, due today, next 7 days, upcoming, missing/invalid date and closed/cancelled. Active actions sort by earliest due date; terminal actions sort after active work. The overdue count excludes terminal actions. This is a live view over loaded company records, not a scheduled notification service.

## Closed legacy action edits

Existing Closed actions can be edited for unrelated fields only when all closure-signature values remain exactly unchanged: responsible, due date, priority, effectiveness criteria, completion evidence, effectiveness status, verifier and verification date. Any changed signature value is subjected to the current closure gate. This is a compatibility behavior, not an exemption from the matching database trigger.
