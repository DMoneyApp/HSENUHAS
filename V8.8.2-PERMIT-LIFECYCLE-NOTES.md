# NUHAS HSE360 V8.8.2 — Permit lifecycle guard candidate

## Local implementation

Added `supabase/v8.8.2-permit-lifecycle-guard.sql` as a staging/review candidate. It is intended to enforce the following permit record rules at the database boundary:

- New records must start as Draft or Pending Approval; initial Approved records require an active organization administrator and the existing full permit validation function.
- Status transitions follow a defined lifecycle. Closed and Expired are terminal; resuming a Suspended permit requires the allowed transition and admin oversight.
- Status changes involving Approved or Suspended permits require organization-admin authority.
- Material edits to Approved or Suspended permit details require an organization administrator; edits that keep an Approved permit active are revalidated through `hse360_validate_permit_authorization`.
- Permit records cannot be changed to a different module or organization.
- The trigger uses a fixed search path and does not grant its function to `public`.

## Important scope limits

This candidate protects changes to the `hse_records` table. It does not itself provide a worksite check-in/permit-to-work execution authorization endpoint, background expiry scheduler, notification delivery, or proof that supervisors physically verified conditions. It complements, rather than replaces, the existing tenant RLS and audited record RPCs.

The migration has **not** been executed or parsed by a live PostgreSQL/Supabase instance. Before use: back up the database, confirm current schema and function signatures, apply only in staging, and test each state transition as admin and non-admin users across at least two organizations. Inspect existing permit statuses first; an unrecognized legacy status will block its next status transition and will require reviewed remediation.
