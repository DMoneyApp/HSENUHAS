# NUHAS HSE360 V8.8.1 — Inspection finding follow-up (local candidate)

## Implemented in the local working tree

- Inspections now require an explicit outcome: Pass, Fail, Pass with findings, or Not completed. The empty/default choice is not accepted.
- Findings count is validated as a non-negative whole number. A Fail or Pass with findings outcome requires at least one finding.
- Findings or declared follow-up require Follow-up = Yes, details of the failed checklist item(s), and immediate-control notes. A not-completed inspection requires a reason.
- Inspection detail view gives prominent visibility to the recorded outcome, failed items, immediate controls and evidence reference.
- Linked corrective-action draft is prefilled with the failed inspection items and references, but remains editable and still requires an owner and due date.
- Source detail finds linked actions via source record ID or source reference. Exact-description duplicates for the same source are flagged in the interface.
- Corrective-action register is now an operational work queue: columns show owner, priority, deadline and source finding; filters support owner, priority and deadline state; the table sorts active items by earliest due date; overdue count is displayed.
- Deadline classification is deterministic and treats invalid/missing dates separately from truly overdue actions; closed/cancelled items are sorted to the end.
- Added a candidate SQL trigger migration (`supabase/v8.8.1-linked-action-deduplication.sql`) intended to prevent concurrent exact-description duplicates for active linked corrective actions. It must be tested in staging and reviewed before use.

## QA performed locally

- `node --check app.js` passed.
- Existing import, certificate reader, static and linked-action smoke tests passed.
- Inspection validator has 11 validation scenarios covering clean pass, missing outcome, contradictory outcome, missing findings, missing follow-up flag, missing finding details, missing controls and incomplete-inspection reason.
- SQL migration static checks passed. No PostgreSQL parser, staging Supabase, authenticated browser or live integration test was run.

## Limitations

- These inspection fields are a structured inspection record, not a configurable checklist scheduler with per-check-item history. That is a future vertical slice.
- Duplicate prevention in the browser is advisory. Server-side enforcement only exists as a candidate migration until it is applied and tested in a non-production database.
- Older inspection records without an outcome show “Not recorded”; when editing one, select and validate an outcome before saving.
- This local candidate has not been deployed to GitHub Pages and does not establish ISO/ADOSH legal compliance.

## Compatibility and closure-control follow-up

- Added a front-end compatibility guard for legacy actions already marked Closed: unrelated edits may proceed only when all closure-critical fields remain byte-for-byte unchanged, aligned with the candidate SQL trigger. Changing any closure-critical value, reopening the action, or creating a new closed action still goes through the current validation rules.
- Added `qa/capa-closure-sql-static-smoke.js` with static checks for the server-side closure trigger requirements. This confirms migration source patterns only; it does not prove PostgreSQL execution or authorization behavior.
