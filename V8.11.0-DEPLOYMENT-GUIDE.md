# V8.11.0 Deployment Guide (Candidate Only)

This release is local only. Do not deploy to GitHub Pages or change production Supabase as part of this candidate.

1. Review the exact branch and commit recorded in the release manifest/report.
2. Preserve the V8.10.9 ZIP, Git bundle and source snapshot; verify their stored SHA-256 values before any rollout.
3. Create a disposable Supabase staging clone and back it up. Inspect the deployed `hse_records` schema, `create_hse_record`, `update_hse_record`, RLS policies, action/CAPA triggers and `auth.uid()` behavior.
4. Reconcile and apply `supabase/v8.11.0-hse-status-history.sql` to staging only. Run `supabase/v8.10.9-attachment-preservation.sql` only if the staging RPC does not already preserve omitted attachment metadata, and reconcile function definitions to avoid replacing newer safeguards.
5. Run permission, status, closure, backdate, reopen, linked-action, timezone and failed-write cases from `V8.11.0-LOCAL-QA-REPORT.md` using real authenticated test accounts.
6. Serve the source bundle in a staging frontend and test desktop, Android/iPhone narrow widths, record detail, attachment display, permits, action queue, imports/exports and dashboard refresh.
7. If staging passes, prepare a separate reviewed production rollout plan and obtain the required organizational approval. This document itself does not authorize production changes.

The candidate migration creates a `BEFORE INSERT OR UPDATE OF status,data` trigger. It appends actor/timestamp history, preserves earlier events, validates closure fields and backdate/reopen reasons, and blocks case closure with open linked actions. It depends on the existing tenant-scoped update RPC permission check. Do not apply until that deployed function is confirmed.
