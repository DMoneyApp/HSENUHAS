# NUHAS HSE360 V8.10.9 — Staging and Deployment Guide

## Current release state

V8.10.9 is a local candidate on `development/v8.10.9`. It has not been pushed or deployed. The observed Pages endpoint served V8.10.8 on 17 October 2026. No production database writes or migrations were made.

## Before staging

1. Back up the staging database and storage metadata. Reconcile its schema/migration history with `supabase/v8-multitenant.sql` and deployed function definitions. Do not run historical SQL files blindly.
2. Confirm the staging frontend has the correct Supabase project URL and publishable key. Never place a service-role key in frontend config.
3. Inspect `supabase/v8.10.9-attachment-preservation.sql`. It redefines the existing `update_hse_record` function and preserves the current V8.6 permit preflight behavior. Confirm its function signature matches the target schema before applying.
4. Apply the migration in staging only. Test with an existing record that has attachment metadata: update with `p_attachment = NULL` and confirm the metadata remains; update with replacement metadata and confirm replacement; attempt an unauthorized edit and confirm denial; inspect the audited UPDATE event. Verify permit records still follow existing validations.
5. Run the local QA commands below. Then perform authenticated browser acceptance across relevant forms, permits, attachments and report/export paths.

## Local checks

From the release source folder:

```powershell
node --check app.js
Get-ChildItem qa -Filter *.js | ForEach-Object { node $_.FullName; if ($LASTEXITCODE -ne 0) { throw "QA failed: $($_.Name)" } }
```

These do not execute SQL, authenticate to Supabase, or prove production behavior.

## Deployment sequence after separate release approval

1. Merge/review the development branch through the team's normal Git process.
2. Apply the verified database migration during the approved change window before distributing clients that rely on it.
3. Publish the cumulative V8.10.9 static files to GitHub Pages using the repository's configured deployment process.
4. Verify the deployed version marker and run authenticated smoke tests in the intended organization.
5. Preserve the migration log, QA evidence, deployment commit and artifact checksums.

No remote push, Pages deployment or production migration is authorized by this local development request; no such action was taken.
